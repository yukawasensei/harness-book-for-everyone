# 第 11 章 · 从失败到修复 / Chapter 11 · From Failure to Fix

> 对照代码：`git checkout ch11` · 上一章：[第 10 章](./ch10.md) · 回到[目录](../README.md)

## 这一章解决什么问题

第 6 章教你用基线签字；第 10 章把所有闸门同时打开。这一章回答签字之后更难的问题：**评测红了，怎么读 trace、怎么在 harness 改一处、怎么重跑对比——而且不把“挡住了错误”当成“任务完成了”。**

本章唯一数据来源是 `evals/runs/compare-trace-fixes.md`。我们在 harness 里加了三道**默认开启、可关闭**的闸门，再拿同一套 case 做定向与全量真跑。数字和结论如下文；小样本、三处同时开启，**不能**把通过率变化归因到某一个开关——单变量机制靠环境变量关闭对照和确定性测试证明。

## 循环：失败 → Trace → 改一处 → 对比 / Fail → Trace → One Fix → Compare

| 步骤 | 做什么 | 证据落在哪 |
|---|---|---|
| 1. 评测发现失败 | `--repeat N` 或全量跑出 FAIL / flaky | 默认 `evals/runs/local/<model>/<run-id>/`；`EVAL_ARCHIVE=1` 时为 `evals/runs/<model>/<run-id>/` |
| 2. 读 trace 定位 | 看原始参数、是否进 executor、有没有产物、模型有没有漏调工具 | 相对路径 `traces/*.jsonl` |
| 3. 在 harness 改一处 | 只动闸门或上下文注入，不改 case prompt 来“洗绿” | `src/tool-inventory.ts`、`src/gates/strict-schema.ts`、`src/gates/json-write.ts` |
| 4. 重跑对比 | 同一批 case，开关默认开；必要时用环境变量关掉做对照 | 新 run 目录 + 对比报告 |

三条失败分别对应三道闸门：

| 闸门 | 针对的失败 | 行为 | 关闭 |
|---|---|---|---|
| 工具清单注入 | 模型声称没有实际已开放的工具（如 `slow`） | 把当前可用工具名写入模型上下文；**不**改白名单 | `HARNESS_TOOL_INVENTORY=0` |
| 原始参数严格校验 | 数字等错误类型被 SDK 转成合法类型后仍执行 | 校验**原始** `toolCall.arguments`，拒绝执行，记 `schema_validation_rejected` | `HARNESS_STRICT_SCHEMA=0` |
| JSON 写前校验 | 非法 JSON（如未转义引号）仍被写入 | 路径策略通过后、确认与写入之前做 `JSON.parse`；记 `json_write_rejected` | `HARNESS_JSON_WRITE=0` |

`harness_start` 会记下三个开关的实际值。旧失败里一次非法 `board.json` 写入，经闸门离线回放会在行列处拒写；证据见 `evals/runs/trace-fixes-verification/archived-failure-replay.json`。

## 定向结果（必须如实读） / Targeted results

改前复用已归档的两模型对照；改后每模型 3 条 case × repeat 5。表中均为**完整验收**，不以 `stop_reason=success` 代替通过。

| 改动 / case | Qwen 改前 | Qwen 改后 | DeepSeek 改前 | DeepSeek 改后 |
| --- | ---: | ---: | ---: | ---: |
| 工具清单 / `tool-timeout-brake` | 4/5 | **5/5** | 5/5 | 5/5 |
| 严格 schema / `custom-tool-schema-conflict` | 5/5 | 4/5 | 0/5 | **0/5** |
| JSON 写前 / `capstone-set-clerk` | 5/5 | 4/5 | 4/5 | **5/5** |
| 三个 case 合计 | 14/15 | 13/15 | 9/15 | 10/15 |

读法（与报告一致）：

1. **工具清单**：Qwen 的 `tool-timeout-brake` 从 4/5 → 5/5；但综合任务里仍出现一次“声称没有 `write`”，问题没有完全消失。
2. **严格 schema**：DeepSeek 错误参数 **5/5 被拒、0 次进入 executor**；模型随后解释或询问，**没有真正修正调用**，任务完成率仍 **0/5**——**挡住了错误 ≠ 任务完成了**。安全边界和完成率是两个指标。
3. **JSON 写前**：DeepSeek 的 `capstone-set-clerk` 4/5 → 5/5，其中一次真实拦下非法 JSON 并让模型重写成功。闸门只保证**语法**合法，不保证业务字段/内容正确。
4. 全量各 20 case × repeat 1：Qwen **20/20**，DeepSeek **19/20**（唯一失败仍是 schema 冲突）。样本量与定向 repeat 5 不同，不能互相覆盖。

## 动手跑 / Reproduce

在 `book/harness` 执行。三个闸门默认开启；凭据由 harness 加载，不要打印环境文件。run 产物默认进 `evals/runs/local/<model>/<run-id>/`（git 忽略）；想留下可提交的归档、复现报告里的路径，命令前加 `EVAL_ARCHIVE=1`。

```bash
cd "$(git rev-parse --show-toplevel)/book/harness"

# 定向：三条相关 case × 5（需要本机 Ollama 或 DeepSeek）
# 默认写 local/；想留档：EVAL_ARCHIVE=1 CASES=... npm run eval -- --repeat 5
CASES=custom-tool-schema-conflict,tool-timeout-brake,capstone-set-clerk \
  NO_PROXY=127.0.0.1,localhost npm run eval -- --repeat 5

MODEL_ID=deepseek/deepseek-flash \
  CASES=custom-tool-schema-conflict,tool-timeout-brake,capstone-set-clerk \
  npm run eval -- --repeat 5

# 全量 20 case × 1（显式传入全部 id，与报告一致）
ALL_CASES=$(node --input-type=module -e 'import fs from "node:fs"; console.log(JSON.parse(fs.readFileSync("cases/cases.json","utf8")).map(c=>c.id).join(","))')
MODEL_ID=ollama/qwen3.8:27b CASES="$ALL_CASES" NO_PROXY=127.0.0.1,localhost npm run eval -- --repeat 1
MODEL_ID=deepseek/deepseek-flash CASES="$ALL_CASES" npm run eval -- --repeat 1

# 对照：关掉三道闸门再跑同一条（单变量观察；默认请保持开启）
HARNESS_TOOL_INVENTORY=0 HARNESS_STRICT_SCHEMA=0 HARNESS_JSON_WRITE=0 \
  CASE_ID=custom-tool-schema-conflict NO_PROXY=127.0.0.1,localhost npm start
```

也可只关一道：例如 `HARNESS_STRICT_SCHEMA=0` 时，数字参数可能再次被 SDK 转换后进入 executor——这正是确定性测试在开关两侧对比的行为。

## 产品拍板

- **拒绝率**和**完成率**分开看：闸门 5/5 挡住不合规调用，若模型从不重试，case 仍可能 0/5。
- 修 harness 用开关和测试证明机制；小样本真跑只能当观察，不能当“三个问题都消失了”的证明。
- 失败保留：不补跑、不改 prompt 把 FAIL 洗成 PASS；trace 相对路径可下钻。
- JSON 写前校验是语法门，产物字段/条数/顺序仍靠第 10 章的产物验收。

## 费曼标准答

1. 评测失败后的正经循环是：读 trace → 在 harness 改一处 → 重跑对比。
2. 工具清单降低“谎称没有工具”的概率，但不能保证综合任务里不再否认已开放工具。
3. 原始参数严格校验挡住静默转换执行；挡住了不等于模型会改对并完成任务。
4. JSON 写前校验拦非法语法并可重试；内容对不对仍看产物检查。
5. 三处默认同开时的通过率变化，不能归因到单个开关；要归因就关开关做对照，并靠确定性测试。

## 下次评测失败时，PM 该追问什么

1. FAIL / flaky 的相对路径 trace 在哪？是漏调工具、参数不合规，还是产物坏了？
2. 这次改的是 harness 闸门，还是只改了 prompt？有没有可关闭的开关做前后对照？
3. **拒绝了几次？完成了几次？** 两张表是否分开汇报？
4. 若闸门拒绝后模型没有重试，产品期望是“停并告警”，还是“必须自动修正到 PASS”？
5. JSON / schema 类失败：拦的是语法/类型，还是业务字段？产物验收有没有独立跑绿？
6. 有没有用补跑或挑结果把失败藏起来？
